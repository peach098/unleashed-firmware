## Шаг 0: воспроизведение и место отказа

- `tools/rd256.sh … before 5 rd1` на прошивке 8d151c59c (01.13): 5/5 `command failed`, в трассе только
  запрос (`before_rd1_*.log`).
- Проба v1 (`p14_probe_v1_before.patch`, `p1_probe_log.txt`): кадр 1-of-256 отброшен декодером,
  `kind=1 fail_idx=8 fail_val=20`. Сэмпл-байты 0…7 нулевые, сэмпл-байт 8 = 0x20 — пауза первого же
  байта запроса 0x22 (слот 34 = сэмпл-байт 34/4 = 8, бит (34%4)·2+1 = 5). `zero_found` ставится на первом
  нулевом сэмпл-байте кадра и сбрасывается только в `iso15693_parser_reset`, поэтому любая пауза после
  него — Fail. Отказывает не «второй байт», а уже первый, если его значение ≥ 4.
- Проба v2 (`p14_probe_v2_raw.patch`, `p2_probe_log_*.txt`): сырая запись всего кадра. Паузы стоят ровно
  там, где их ждёт декодер (байт i, значение v → сэмпл-байт 64·i + v/4, бит (v%4)·2+1), EOF 0x04 ровно на
  границе байта (сэмпл-байт 832 = 13·64 для read single, 896 = 14·64 для read multi). Дрейфа выборки нет
  (таймер сэмплов пересинхронизируется на каждой паузе), менять нужно только логику декодера.
- Причина 2 (EOF→RxEnd) подтверждена хост-тестом-мутацией (`host/parser_test_mutation_thread_eof.txt`):
  если EOF ищет поток на границе байта, RxEnd наступает через 31 сэмпл-байт после EOF = 31 · 75.5 мкс =
  **2.34 мс** (поток будится раз в 32 сэмпл-байта, а EOF 1-of-256 — всегда первый символ новой порции:
  64·N + 1). На устройстве до правки это не измерить: старый декодер до EOF не доходит.

## Исправление декодера (`e13952dce`, lib/signal_reader/parsers/iso15693/iso15693_parser.c)

- Каждый байт проверяется отдельно: 64 сэмпл-байта, ровно одна пауза, во второй половине слота
  (сэмпл-байт равен одному из 0x02/0x08/0x20/0x80). Нет паузы, вторая пауза (в том же или другом
  сэмпл-байте), пауза в первой половине слота, EOF внутри байта → Fail и перезапуск парсера, как в 1-of-4.
- Переполнение `parsed_frame` → Fail (как было).
- EOF 1-of-256 детектируется в ISR (`signal_reader_callback`) только на границе байта
  (`symbols_received % 64 == 0`); поток дочитывает буфер и возвращает Success. Работает с буфером 2×32 и
  `iso15693_parser_consume` из 01.12; буфер возвращается только для незавершённого кадра (как в 1-of-4).
- `zero_found`, `byte_idx` удалены, добавлено `pause_found`. Декодер 1-of-4 и его ветки в колбэке не
  изменены.

## Хост-тест (`host/`)

`host/run.sh` (из корня репозитория) собирает неизменённые `iso15693_parser.c` и `bit_buffer.c` с
заглушками (`host/stubs`; signal_reader — в `parser_test.c`: `signal_reader_start` сохраняет колбэк, тест
играет ISR по одному сэмпл-байту, «поток» вызывает `iso15693_parser_run` с задержкой 0…31 сэмпл-байт;
после рестарта нулевые сэмпл-байты до первого фронта отбрасываются). ASan+UBSan.

Случаи: read single/multi PM3, все 256 значений (по возрастанию/убыванию), случайные кадры 1…40 байт со
случайной задержкой потока, кадр 1024 байта (ёмкость), 1025 байт → отказ (оба кодирования); 1-of-256 и
1-of-4 дают одинаковые байты; RxEnd в тот же сэмпл-байт, что EOF (задержка 0), в обоих режимах;
`iso15693_parser_is_1outof256()` отражает кодирование кадра. Негативные (кадр отвергнут, следующий
корректный принят): две паузы в разных/одном сэмпл-байте, байт без паузы, пауза в первой половине слота
(0x04, 0x01), EOF внутри байта, нет EOF, шум, 0xAA; обрыв плохого кадра не влияет на следующий; 1-of-4:
EOF без паузы на границе байта (01.12) и невалидный символ; принудительные режимы.
Результат: `parser_test.txt` **PASSED 0/256**; код до правки — `parser_test_before.txt` 121/201 FAIL.

## EOF→RxEnd и FDT (DWT)

Проба v3 (`p14_probe_v3_on_fix.patch`; `p3_*` на `e13952dce`, `p4_*` на `780487f52`): DWT в ISR при EOF,
на RxEnd в воркере и при старте DMA ответа (`p3_dwt.txt`, `p4_dwt.txt`, n=10 на строку, медиана/мин/макс):

| сборка | кодирование | ответ | ISR EOF → RxEnd, мкс | ISR EOF → DMA, мкс |
|---|---|---|---|---|
| e13952dce (1385 для всех) | 1-of-4 | 7 B (read single) | 71.7 / 71.5 / 71.8 | 321.0 / 320.5 / 321.2 |
| | 1-of-4 | 35 B (read multi 8) | 75.0 / 74.8 / 79.1 | 324.3 / 323.9 / 328.2 |
| | 1-of-256 | 7 B | **53.4** / 53.2 / 57.4 | 302.5 / 302.2 / 306.4 |
| | 1-of-256 | 35 B | **53.2** / 47.9 / 53.4 | 302.5 / 302.3 / 302.6 |
| 780487f52 (1-of-256: 1137) | 1-of-4 | 7 B | 72.2 / 66.6 / 75.2 | 320.7 / 315.1 / 323.7 |
| | 1-of-4 | 35 B | 75.5 / 75.3 / 80.2 | 323.9 / 323.7 / 328.7 |
| | 1-of-256 | 7 B | 54.3 / 48.8 / 57.8 | **321.1** / 321.0 / 324.5 |
| | 1-of-256 | 35 B | 54.3 / 54.3 / 54.3 | **321.3** / 321.1 / 321.3 |

Почему 1-of-256 быстрее: EOF ловится в ISR одинаково, но в 1-of-4 после EOF потоку остаётся декодировать
хвост (до 31 символа: 20 для read single, 24 для read multi), а байт 1-of-256 — ровно две порции по 32, к
EOF буфер пуст. Поэтому t_rx(1-of-256) постоянен для любой длины.

Без режим-зависимой компенсации SOF по PM3 был **297.3 мкс** (мин. 292.6) — раньше t1min (4192/fc =
309.1 мкс) (`after_*`). Добавлена компенсация (`780487f52`, furi_hal_nfc_iso15693.c):

    COMP_1OF256 = COMP - (t_rx(1-of-4) - t_rx(1-of-256)) * fc = 1385 - 18.3 us * 13.56 MHz = 1137 fc

`FuriHalNfcListenerCompensation` получил необязательный `get_fdt()` (furi_hal_nfc_tech_i.h, внутренний
заголовок), `furi_hal_nfc_timer.c` берёт его, если задан; ISO15693 возвращает 1137, когда парсер принял
кадр в 1-of-256 (`iso15693_parser_is_1outof256`, не в SDK API), иначе 1385. `ISO15693_3_FDT_LISTEN_FC`
(4320) и компенсация 1-of-4 (1385) не менялись. Проверка: EOF→DMA 1-of-256 стал 321.1 мкс = 1-of-4 read
single (320.7…321.0).

## Ветки и коммиты

- Артефакты: `fnfc-01.14-1of256`: `e13952dce`, `780487f52` (код) + коммит nfc_dumps.
- Код-only: `fnfc-01-f1g-code` от `fnfc-01-f1f-code` (491370cc6). **Важно:** f1f-code не содержит парсер
  01.12 (`fnfc-01-f1e-code` и `fnfc-01-f1f-code` — соседние ветки от a7e73b089), а исправление опирается на
  него (буфер 2×32, `symbols_received`, `consume`). Поэтому в f1g сначала cherry-pick четырёх код-коммитов
  f1e (656aaf57c, ff37b86e0, d89408f02, e19f789f9), затем 6e11acde6 и cc7b6d0fb. Файлы парсера и HAL в f1g
  совпадают с артефакт-веткой. Сборка `./fbt DEBUG=0` чистая.
- Устройство оставлено на чистом release 780487f52 (`release_device_info.txt`).

## Что посмотреть ревьюеру

- `get_fdt()` в `FuriHalNfcListenerCompensation` — новый необязательный хук в общем HAL-таймере
  (furi_hal_nfc_timer.c / furi_hal_nfc_tech_i.h). Альтернатива без правки общих файлов (ожидание в
  `furi_hal_nfc_iso15693_listener_tx`) хуже: тратит запас обработчика.
- Компенсация выбирается по кодированию, но по сути t_rx зависит от «хвоста» несчитанных символов в момент
  EOF; у 1-of-4 он меняется с длиной запроса (71.7 мкс при 20 символах, 75 мкс при 24) — это известная
  разница read single / read multi из 01.11, не трогалась.
- Кадр из одного EOF (01.13, Write/Lock с option flag) идёт по пути ParseSoF: парсер сброшен в 1-of-4,
  берётся 1385, а t_rx у него, как у 1-of-256 (хвоста нет) — ответ, вероятно, ~18 мкс раньше t1nom. Это
  было и до 01.14, не измерялось; кандидат на отдельную карточку.
- Пропущенный EOF в 1-of-256 (пауза EOF не попала в выборку, механизм B из 01.12) не завершает кадр: после
  64 пустых сэмпл-байт Fail, запрос теряется. Аналог правила 1-of-4 «символ без паузы = EOF» в 1-of-256
  возможен только с задержкой ~600 мкс (нулевой сэмпл-байт на границе — нормальные данные). В 1-of-256
  сериях (≈300 запросов, включая 3 dump-а) потерь не было.
- Выбросы SOF 330.4 мкс (2/20 в `fix2`) — выше t1max 323.3 мкс; на DWT не видны.

## Открытые вопросы (человеку)

- Используют ли целевые турникеты 1-of-256 — неизвестно, реальные турникеты не трогались.
- Ответ на низкой скорости (флаг 0x02 сброшен) и FSK (флаг 0x01) не поддержаны: листенер всегда отвечает на
  высокой скорости одной поднесущей. Для запросов PM3 `-2` с флагами 0x22 это корректно; ридер, который в
  1-of-256 просит низкую скорость, ответ не поймёт.
